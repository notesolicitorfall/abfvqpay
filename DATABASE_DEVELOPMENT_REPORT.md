# Разработка базы данных

## 1. Назначение базы данных

В рамках разработки информационной системы интернет-провайдера была спроектирована и реализована база данных для хранения сведений о сотрудниках, клиентах, тарифах, договорах, адресах подключения, оборудовании, IP-адресах, платежах и обращениях клиентов. База обеспечивает сохранность информации между запусками программы и позволяет связывать данные разных разделов системы.

## 2. Проектирование ER-модели

На этапе проектирования в MySQL Workbench была построена ER-модель. Она использовалась для наглядного представления сущностей предметной области, состава таблиц и связей между ними. MySQL Workbench в данном проекте применялся именно как средство визуального моделирования: приложение не подключается к MySQL, а созданная в Workbench модель не является рабочей базой данных системы.

При построении модели были выделены сущности, соответствующие основным объектам работы интернет-провайдера. Для каждой сущности определены атрибуты, первичный ключ и необходимые связи. Например, договор содержит ссылки на клиента, тариф и адрес подключения; платеж связан с договором; оборудование относится к клиенту; заявка относится к клиенту и может быть связана с договором. Такое разделение данных по таблицам позволяет хранить информацию об объектах отдельно и связывать её с помощью идентификаторов.

## 3. Реализация базы данных средствами SQLite

После разработки ER-модели структура была реализована не в MySQL, а в SQLite. В приложении используется файл `internet_provider.db`, расположенный рядом с программными файлами. SQLite — встраиваемая реляционная СУБД: база хранится в одном файле, а для работы приложения не требуется запускать отдельный сервер баз данных.

Создание и использование базы реализовано на языке Python с помощью стандартного модуля `sqlite3`. SQL-описание таблиц находится в файле `app.py`. При запуске программы функция инициализации проверяет структуру базы и создаёт отсутствующие таблицы. Таким образом, ER-модель в MySQL Workbench служила проектной схемой, а фактическое создание таблиц и обработка данных выполняются приложением через SQLite.

В реализованной базе предусмотрены следующие таблицы:

| Таблица | Назначение |
|---|---|
| `employees` | Учётные записи сотрудников и данные для проверки пароля. |
| `clients` | ФИО, контакты, дата регистрации и статус клиента. |
| `tariffs` | Название тарифа, скорость, стоимость, описание и статус. |
| `addresses` | Город, улица, дом и квартира. |
| `contracts` | Номер договора, клиент, тариф, адрес, сотрудник, даты и статус. |
| `devices` | Тип и модель оборудования, MAC-адрес, клиент и статус устройства. |
| `ip_addresses` | IP-адрес, его тип, связанный адрес подключения и статус. |
| `payments` | Договор, сумма, дата, способ оплаты и статус платежа. |
| `support_tickets` | Клиент, договор (если указан), тема, описание, статус и даты обращения. |

## 4. Связи и контроль целостности

Связи между таблицами реализованы внешними ключами. Например, в таблице договоров поля `client_id`, `tariff_id` и `address_id` указывают на соответствующие записи клиентов, тарифов и адресов. Поле `contract_id` в таблице платежей связывает платёж с договором. Это позволяет хранить связанные сведения без многократного дублирования всей информации о клиенте, тарифе или договоре.

Для сохранения корректности данных применяются ограничения целостности: первичные ключи, обязательность значений для необходимых полей (`NOT NULL`), уникальность отдельных значений (`UNIQUE`) и проверки допустимых числовых значений (`CHECK`). Например, номер договора, MAC-адрес и IP-адрес не должны повторяться, скорость тарифа должна быть положительной, а сумма платежа — неотрицательной. Для некоторых полей статуса заданы значения по умолчанию. При подключении к SQLite приложение включает проверку внешних ключей.

В базе также предусмотрено поле `owner_id`, связывающее рабочие записи с сотрудником. Это используется для разграничения данных пользователей приложения. Для ускорения выборок создаются индексы по полям владельца, а также индекс для договоров по сотруднику и дате начала.

## 5. Инициализация и работа с данными

При первом запуске приложения создаётся файл базы и необходимые таблицы. Если база пуста, система добавляет демонстрационные записи, чтобы можно было ознакомиться с работой разделов. Для существующей базы предусмотрена проверка структуры и добавление некоторых новых столбцов при их отсутствии; это позволяет обновлять схему без удаления уже сохранённых записей.

Приложение выполняет операции чтения и изменения данных через SQLite: отображает записи в разделах интерфейса, позволяет добавлять и редактировать информацию, а удаление выполняет с учётом ограничений связей. SQL-запросы к базе выполняются из Python. Для хранения паролей сотрудников используются соль и криптографический хеш, а не открытый текст пароля.

## 6. Результат разработки

В результате была подготовлена ER-модель в MySQL Workbench для визуального анализа структуры и связей, а затем реализована рабочая реляционная база данных SQLite, используемая настольным приложением. Разделение этапов позволило сначала представить состав сущностей и их взаимосвязи в наглядном виде, а затем перенести эту структуру в фактическую реализацию на SQLite. MySQL Workbench в готовой системе не выполняет хранение данных и не используется приложением для подключения; постоянное хранение и обработка информации осуществляются в файле `internet_provider.db` средствами SQLite и модуля Python `sqlite3`.
